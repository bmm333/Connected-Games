# ADR007: MQTT with Eclipse Mosquitto as the Message Broker

- **Status:** Accepted
- **Date:** 2026-10-26
- **Scope:** Message broker for game events and live displays

## Context

Game events flow from the tables to the
platform, and live displays in the browser need push updates. Devices are small and
connections are unreliable.

## Decision

1. We use **MQTT** with **Eclipse Mosquitto 2** (`eclipse-mosquitto:2.0.22`).
2. The broker exposes MQTT on port **1883** and MQTT over **WebSockets on port 9001**,
   so browser clients (simulator, table display) can subscribe directly.
3. Persistence is enabled, so retained messages survive a restart.
4. In the local environment the broker accepts anonymous clients without TLS; the
   configuration lives in `infra/docker/mosquitto/mosquitto.conf`.
5. Channels and messages are defined in AsyncAPI (ADR005).

## Consequences

### Positive

- MQTT is light enough for small devices and tolerates unreliable networks.
- Browsers subscribe over WebSockets without an extra server.

### Costs and trade-offs

- We operate the broker ourselves

## Alternatives considered

- **REST from the devices:** rejected. No push, and live updates would need polling.
- **Kafka:** rejected. Too heavy in memory and operations for this load.
- **RabbitMQ (AMQP):** rejected. MQTT is the IoT standard and the protocol suggested by
  the course.
- **EMQX:** rejected More features, but heavier than Mosquitto.
