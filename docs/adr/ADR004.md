# ADR004: Clean Architecture in Every Service, Enforced by ArchUnit

- **Status:** Accepted (applied so far in `catalog`: domain and application layers)
- **Date:** 2026-10-26
- **Scope:** Internal structure of the backend services (the web follows ADR001)

## Context

We want business rules that can be tested without a database, a web server or a broker,
and infrastructure that can be replaced without rewriting them. Architecture rules that
live only in documents erode within weeks.

## Decision

Every service with business logic uses the same packages:

```
com.connectedgames.<service>
├── domain            entities and value objects, pure Java
├── application       use cases and ports
│   ├── port/in       what the service offers (use case interfaces)
│   └── port/out      what it needs (repositories, publishers)
├── adapters
│   ├── in/web        REST controllers
│   ├── in/mqtt       message listeners
│   └── out/persistence   database access
└── infrastructure    Spring configuration and wiring
```

Conventions, as implemented in `catalog`:

1. **Domain:** immutable records, typed identifiers (`VenueId`, `TableId`,
   `GameTypeId`), value objects (`QrCode`) and invariants checked in constructors.
   No Spring, no JPA.
2. **Application:** use case interfaces in `port/in`, repository interfaces in
   `port/out`, services without Spring annotations. A missing resource raises
   `NotFoundException`; inconsistent data raises `IllegalStateException`.
3. **Pragmatism:** simple read-only operations are grouped in one use case
   (`BrowseCatalogUseCase`) instead of one interface each.
4. **Tests:** use cases are tested with in-memory fakes of the outbound ports rather
   than mocks.
5. **Enforcement:** the shared `architecture-rules` module defines ArchUnit rules
   (onion architecture; no Spring or JPA in `domain`). Every service except `gateway`
   runs them in its test suite, and a violation fails the build.

## Consequences

### Positive

- Domain and use cases are tested in milliseconds, without containers.
- Violations are caught by the build, not by reviewers.

### Costs and trade-offs

- Mapping code between persistence, domain and API models.
- More files than a controller-service-repository layout.

## Alternatives considered

- **Controller, service and repository packages with JPA entities as the domain:**
  rejected. It couples business rules to the database model.
- **Architecture rules without automated checks:** rejected. They drift quickly.
- **Mocks for every test:** rejected. Fakes test behaviour and survive refactoring.
