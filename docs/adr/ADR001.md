# ADR001: Web Application Architecture

- **Status:** Accepted
- **Date:** 2026-10-25
- **Scope:** Frontend and web application architecture

## Context

Connected Games needs one client application that can serve different audiences and
devices:

- players joining a game from a table QR code;
- kiosk devices displaying public and live information;
- venue administrators using an operational console.

The client must be responsive, testable and usable during temporary connectivity loss.
It should run in a browser and provide a path to Android and iOS packaging without
duplicating the UI. The frontend must also remain independent from transport,
storage and platform APIs so that those integrations can evolve separately.

This ADR records the web decisions implemented so far. Backend service and deployment
decisions are outside its scope.

## Decision summary

We will:

1. build the client with React, TypeScript and Vite;
2. expose separate Player, Kiosk and Console surfaces from one codebase;
3. use Clean Architecture and dependency inversion in the frontend;
4. use shared OpenAPI contracts to generate typed API declarations;
5. hide QR scanning and storage behind platform-independent interfaces;
6. make server state offline-aware with TanStack Query and persisted caching;
7. support PWA installation and Capacitor-based native packaging;
8. validate the web application with linting, tests and builds in CI.

## Decisions

### 1. React, TypeScript and Vite

The web application uses React 19 and TypeScript, bundled with Vite. This gives us a
typed UI foundation, fast local development and multiple build entry points from one
frontend codebase.

Tailwind CSS is used for styling. Shared UI components, design tokens, theme handling
and the application shell are kept in reusable UI modules. Inter is bundled as the
application font.

### 2. Separate application surfaces

The client is split into three independently routable surfaces:

- **Player:** QR onboarding, table discovery, lobby, match, profile and statistics;
- **Kiosk:** attract, queue, leaderboard and live display views;
- **Console:** venue administration, tables, live matches, statistics, screens and
  device/hub management.

Each surface has its own entry point, router and composition root. Surface-specific
navigation and dependencies remain explicit, while domain logic and visual primitives
can be shared. The build produces distinct Player, Kiosk and Console bundles.

### 3. Clean Architecture and dependency inversion

The frontend is organized around explicit boundaries:

- `domain` contains business types and repository interfaces;
- `use-cases` contains application orchestration;
- `infrastructure` contains HTTP, QR, storage and platform implementations;
- `surfaces` contains composition roots, routing and views;
- `ui` contains reusable components, themes and design tokens;
- `shared` contains cross-cutting API, persistence, offline and realtime support.

The domain does not depend directly on `fetch`, Capacitor, IndexedDB, React Query or
browser APIs. Implementations are selected in the surface composition roots. For
example, catalog access is exposed through a repository port and implemented by an
OpenAPI-backed adapter, while QR scanning is implemented by browser or native adapters.

This keeps business rules testable without a browser or a live API and allows a
platform integration to be replaced without rewriting use cases.

### 4. Contract-driven API integration

The client consumes the OpenAPI 3.1 contracts in `contracts/openapi`. The current
contracts describe:

- catalog operations for venues, tables, game types and QR table resolution;
- match operations for current match data, match details and match timelines.

The contracts define UUID identifiers, explicit enums, authentication requirements and
structured problem responses. QR table resolution and public current-match access are
available without authentication because a guest must be able to enter from a table
QR code.

TypeScript declarations are generated from the OpenAPI documents with
`openapi-typescript`, and `openapi-fetch` is used for typed HTTP access. Generated
types are therefore derived from the shared contract instead of being maintained
independently in the frontend.

### 5. QR onboarding and platform adapters

QR codes are the primary entry point for table and device onboarding. The client
supports:

- browser scanning through camera access and `BarcodeDetector` when available;
- native scanning through a Capacitor barcode scanner plugin;
- manual code entry when scanning is unavailable;
- separate pairing/authentication flows for Player, Kiosk and Console surfaces.

The scanner is hidden behind a domain repository interface. Session credentials and
other key-value data use a platform storage abstraction:

- Capacitor Preferences on native platforms;
- IndexedDB in the browser.

Authentication responses are mapped at the infrastructure boundary into the domain
`Session` model, so UI code does not depend on backend response naming or shape.

### 6. Offline-aware client data

TanStack Query is used for server state. Query data is persisted through an IndexedDB
persister in the browser and the platform storage abstraction on native platforms.
Queries use an offline-first network mode, a two-minute default stale time and a
24-hour persisted cache retention period.

Four-hundred-level client errors are not blindly retried, while transient failures
receive bounded retries. The application can render previously fetched data during
temporary connectivity loss without treating an unavailable mutation as successful.
Realtime updates and offline write/outbox behavior remain explicit future work rather
than being hidden inside the query cache.

### 7. PWA and native packaging

The Vite application is configured as a Progressive Web App with automatic update
registration, an installable manifest and Workbox caching.

- Static assets use cache-first behavior.
- Selected catalog and game metadata reads use network-first behavior with a short
  network timeout.
- API, WebSocket and MQTT paths are excluded from the document navigation fallback.

Capacitor is included for Android and iOS packaging. Native packaging reuses the same
React application and swaps platform adapters where browser APIs are insufficient.
This avoids maintaining separate native UI implementations for the initial surfaces.

### 8. Quality gates and delivery

The CI workflows are path-based. The web workflow runs on pull requests and pushes
affecting the web application or OpenAPI contracts. It installs the locked npm
dependencies and runs:

1. ESLint;
2. Vitest unit and component tests;
3. builds for all web surfaces.

The services workflow runs the Gradle build and tests only for changed microservices.
Changes to shared Gradle configuration, the service settings, Docker Compose or the
PostgreSQL initialization scripts run the checks for every microservice. The backend
services covered by this workflow are Gateway, Identity, Catalog, Match, Tournament
and Stats.

The current test suite covers domain behavior such as match scoring, use cases such
as QR authentication and table resolution, shared API/offline behavior and QR page
flows.

## Consequences

### Positive consequences

- Business rules can be tested independently of React and platform APIs.
- One client foundation supports browser, kiosk and mobile/native targets.
- Surface boundaries prevent administrator concerns from leaking into player flows.
- OpenAPI contracts provide a shared integration source and generated client types.
- Offline persistence improves resilience in venues with unreliable connectivity.
- Architecture boundaries make infrastructure replacements less costly.

### Costs and trade-offs

- There are more folders, interfaces and composition code than in a single-layer
  frontend.
- Contract changes require coordination between OpenAPI files, generated types and
  API adapters.
- Persisted caches introduce invalidation and stale-data concerns.
- Supporting browser and native adapters increases platform testing requirements.
- Offline writes and realtime synchronization still require dedicated design decisions.

## Current implementation status

Implemented or established:

- React/TypeScript/Vite web foundation;
- Player, Kiosk and Console entry points and routing;
- shared UI primitives, theme support and design tokens;
- domain ports, use cases and infrastructure adapters for initial QR, authentication
  and catalog flows;
- generated OpenAPI TypeScript declarations;
- offline query persistence and platform key-value storage;
- PWA configuration and Capacitor Android/iOS projects;
- match scoring domain model and tests;
- API, offline, use-case and QR page tests;
- web lint, test and multi-surface build CI.
- path-based CI for all backend microservices.

Still to be completed or intentionally left open:

- complete UI and use-case flows for all player, kiosk and console features;
- complete realtime client subscriptions;
- robust offline write queues and synchronization conflict handling;
- final API error, loading and empty-state UX across all surfaces;
- production performance budgets and browser/device compatibility coverage;
- accessibility and end-to-end test coverage for the complete application.

## Alternatives considered

### One frontend application with runtime role branching

Rejected for the initial structure. A single route tree with role checks would make
Player, Kiosk and Console concerns harder to isolate and would encourage accidental
sharing of navigation and dependencies. Separate surfaces retain one codebase while
keeping product boundaries visible.

### Direct API calls from React components

Rejected. Direct calls couple UI code to transport details, make testing harder and
duplicate mapping and error behavior. Repository ports and use cases keep that
coupling at the infrastructure boundary.

### Browser-only storage

Rejected. The same application must run on native platforms, where Capacitor
Preferences is the platform-native storage mechanism. A storage abstraction lets the
domain use one interface while each platform uses its appropriate implementation.

### Separate native UI applications

Rejected for the initial product. Maintaining independent Android, iOS and web UIs
would duplicate surface behavior and increase the cost of keeping flows consistent.
Capacitor provides native packaging while preserving the shared React UI.

## Revisit criteria

This ADR should be revisited if:

- the web and native applications diverge enough to require separate presentation
  architectures;
- offline writes become a core requirement and require formal conflict resolution;
- realtime traffic requires a different client transport or state-management strategy;
- surface-specific performance or accessibility constraints require separate bundles or
  rendering approaches;
- the current frontend boundaries create measurable development overhead without
  corresponding testability or reuse benefits.
