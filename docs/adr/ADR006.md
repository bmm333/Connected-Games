# ADR006: PostgreSQL with a Schema and a User per Service

- **Status:** Accepted
- **Date:** 2026-10-26
- **Scope:** Database of the backend services

## Context

Each microservice must own its data, and no service may read another service's
tables, even by mistake. Everything must also run on a single machine.

## Decision

1. **PostgreSQL** is the database of every service (`postgres:18.6` in the local
   environment, ADR008).
2. **One database, one schema and one database user per service** (`identity`,
   `catalog`, `match`, `tournament`, `stats`; the gateway has no database). Each user
   owns its schema, has its `search_path` set to it, and has no permission on the
   other schemas.
3. An initialization script (`infra/docker/postgres/init/01-service-schemas.sh`)
   creates the users and schemas, with passwords taken from `.env`.

The isolation was verified: the `catalog` user gets `permission denied for schema
match` when it reads a table of `match`.

## Consequences

### Positive

- Ownership is enforced by the database, not by convention.
- One PostgreSQL instance keeps memory use low.

### Costs and trade-offs

- Data needed by several services is shared through APIs and events, never through
  queries across schemas.

## Alternatives considered

- **One shared schema for all services:** rejected. Nothing would stop a service from
  reading or changing another service's tables.
- **One PostgreSQL instance per service:** rejected. Too much memory on one machine.
