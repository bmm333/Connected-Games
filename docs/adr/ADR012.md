# ADR012: Game Type, Tournament Link and Tenant in Match Events

- **Status:** Accepted
- **Date:** 2026-11-20
- **Scope:** Extra data carried by `MatchStarted` and `MatchCompleted`

## Context

Statistics need to know which game was played, a tournament needs to know which match of
its bracket was played, and both must keep the data of each organization apart (issue #42).
The hub works offline, and the match service does not know tables or tournaments: catalog
and tournament do.

## Decision

1. `MatchStarted` carries `gameTypeId` (required): the game of the table when the match
   starts. The match service stores it, shows it in `Match` and copies it to `MatchCompleted`.
2. `MatchStarted` carries `tournamentMatchId` (optional). The operator picks the match of
   the bracket in the console, the console gives it to the hub, and the hub writes it in the
   event. No channel from the cloud to the hubs is added. When `MatchCompleted` arrives,
   tournament checks that the participants are those of that match of the bracket, and
   discards it, with a log, if they are not.
3. The `tenantId` of the envelope is the organization of the venue. The match service stores
   it and copies it to `MatchCompleted`. Stats and tournament keep it on every row, and every
   query of a manager is filtered by the `organizationId` of the token. The isolation test
   uses two organizations (issue #42).
4. `participantId` stays an opaque string: for individual matches it is the `playerId`.
   Squads have no owner service yet: tournament decides it in its contract.

## Consequences

### Positive

- The history stays right if a table changes game later.
- The hub needs no new channel: tournament matches are chosen locally, also when the cloud
  is slow.
- Every row has its tenant, so isolation can be filtered and tested.

### Costs and trade-offs

- The hub declares game and tenant and the cloud does not check them. The hub is
  authenticated per venue; checking them against catalog is a later hardening.
- Hubs and simulator must send `gameTypeId`: the web simulator needs the new field.
- Team matches work for statistics, but without squad management.

## Alternatives considered

- **The match service asks catalog for the game:** rejected. A runtime dependency, and a
  wrong history if the table changes.
- **Consumers read the table in catalog:** rejected for the same reason.
- **Tournament matches bound by table and time:** rejected. Fragile, and two matches can
  overlap.
- **Bound by participants only:** rejected. Offline and guest matches have no
  `participantId`, and the same pair can meet twice.
- **Command channel from the cloud to the hub:** rejected for now. A new channel, and
  offline cases to design.
