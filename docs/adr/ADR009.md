# ADR009: Git Workflow with Task Branches and Pull Requests

- **Status:** Accepted
- **Date:** 2026-10-26
- **Scope:** Branching and integration of changes

## Context

We are working in parallel on one monorepo. Changes must be visible to both before
they reach the shared branch.

## Decision

1. `develop` is the integration branch and the repository's default branch; `main`
   holds released states.
2. Every task has its own short-lived branch (`feat/...`, `chore/...`, `docs/...`),
   and reaches `develop` through a pull request.
3. Commit messages and pull request titles follow Conventional Commits
   (`feat(catalog): ...`, `chore(infra): ...`).
4. Contract changes have their own pull request (ADR005).

## Consequences

### Positive

- Every change can be reviewed before it reaches `develop`.
- The history shows one entry per task.

### Costs and trade-offs

- Branches must be kept up to date with `develop` to avoid conflicts.
