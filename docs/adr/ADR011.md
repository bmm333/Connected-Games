# ADR011: Match Completed Event Published Through a Transactional Outbox

-   **Status:** Accepted
-   **Date:** 2026-11-20
-   **Scope:** How stats and tournament learn that a match is closed

## Context

Stats and tournament are built from what happens at the tables. The match service is the only
one that validates and deduplicates the events of the hubs, so the other two must
learn from it that a match is closed, with its final result.

## Decision

1. The match service publishes one `MatchCompleted` message for each closed match
   on `platform/matches/completed` (MQTT, QoS 1, not retained). The message is defined
   in AsyncAPI (ADR005).
2. The message is first written to an `outbox_event` table, in the same transaction that
   closes the match. A publisher sends the unpublished rows in order and marks them as
   published. Delivery is at least once.
3. Stats and tournament are idempotent on `matchId`. Each has its own persistent MQTT
   session (fixed client id, clean session off), so messages wait while it is down.
4. The topic is outside `venues/...`, so the broker can forbid the hubs to publish under
   `platform/`.
5. The message is sent for every outcome, `CANCELLED` included: stats ignores cancelled
   matches, tournament may need them.

## Consequences

### Positive

-   A match closed in the database is never lost, even if the broker is down at that moment.
-   The services stay independent: no shared tables, no polling.
-   Deduplication and replay stay in one place, the match service.

### Costs and trade-offs

-   The match service gets an outbox table and a publisher, and runs as a single instance, like its ingestion.
-   Consumers must accept duplicates.
-   A consumer created after some matches were played does not receive them. The published rows are kept, so a backfill is a republish.

## Alternatives considered

-   **Publish after the commit, without outbox:** rejected. If the service or the broker dies between the commit and the publish, the message is lost: acceptable for a live score, not for stats and standings.
-   **Stats and tournament subscribe to the topic of the hubs:** rejected. They would repeat deduplication and replay, and could disagree with match.
-   **REST polling of the match service:** rejected. Coupling and delay, with no push.
-   **A shared database:** rejected by ADR006.
