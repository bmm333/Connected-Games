# ADR002: Six Microservices in  a Monorepo 

- **Status:** Accepted
- **Date:** 2026-10-26
- **Scope:** Service boundaries and repository layout

## Context

PISSIR course requires a microservice architecture. We are a team of two and have five
weeks, so the number of services must stay small. Contracts, services, web and
documentation often change together in the same feature.

## Decision

### Services

Six Spring Boot services, generated with Spring Initializr under `services/`:

| Service | Responsibility |
|---|---|
| `gateway` | Single entry point for the clients |
| `identity` | Users, roles and authentication |
| `catalog` | Organizations, venues, tables, game types, QR resolution |
| `match` | Game events, match state and scores |
| `tournament` | Tournaments, registrations, standings |
| `stats` | Statistics built from match data |

Each service owns its own database schema

### Repository

We Decided one **monorepo** with `contracts/`, `services/`, `edge/`, `web/`, `infra/`,
`datasets/` and `docs/`. The services form one Gradle multi-project build with a shared
wrapper and version catalog.

To keep the services independent inside one repository:

1. no shared domain code between services: only the contracts and the
   `architecture-rules` test module are shared;
2. no service reads another service's tables

## Consequences

### Positive

- A contract change, its implementation and the generated client types can land in one
  pull request.
- One clone gives the whole system.

### Costs and trade-offs

- Discipline is needed to keep services independent inside one repository.
- CI must build only what changed to stay fast.

## Alternatives considered

- **One repository per service:** rejected. Contract changes would need coordinated
  pull requests across repositories.
- **A modular monolith:** rejected. The course requires microservices.
- **More services (devices, notifications):** rejected. Too many for the given time.
